# ADR-0016 · 用按天预聚合的表加速统计查询（中文稿）

- **日期**：2026-10-24
- **状态**：提议
- **相关**：PR #170

## 目标

加快日、周、月统计和全部历史这四个页面的后端查询。全部历史从点击到画完要 445 ms，其中 370 ms 是后端查询。验收标准是 ≤ 150 ms。

## 要加速的两个查询

| 页面上显示的 | 后端函数 | 全部历史现在要 |
|---|---|---|
| 每天的柱子。各分类时长、总时长由前端把柱子加起来 | `day_category_time` | 234 ms |
| 应用排行：每个应用的总时长 | `top_apps` | 136 ms |

不在这次范围内：应用详情页（`app_detail`）、日统计的小时柱。

## 性能瓶颈

两个函数每次都走三步：

1. 读出范围内的全部记录。全部历史有 24 万行。
2. 给每一行找分类。
3. 按天、按分类（或者按应用）把秒数加起来。

## 设计

### 1. 新表 `daily_usage`： 按天预聚合

一行存「日期 × 设备 × 进程 × 网站」的秒数合计。跨午夜的记录先按午夜切开，两段分别算进两天。比如 `activities` 里有这三行：

| local_date | device | process | url_host | 秒 |
|---|---|---|---|---|
| 2026-10-21 | mac-a | Google Chrome | github.com | 1200 |
| 2026-10-21 | mac-a | Google Chrome | github.com | 2200 |
| 2026-10-21 | mac-a | Code | （无） | 12600 |

在 `daily_usage` 里会变成两行：

| local_date | device_id | process_name | url_host | secs |
|---|---|---|---|---|
| 2026-10-21 | mac-a | Google Chrome | github.com | 3400 |
| 2026-10-21 | mac-a | Code | `''` | 12600 |

全部历史从 24 万行变成 4,863 行。主键是前四列，表用 `WITHOUT ROWID`。没有网站时存 `''` 而不是 NULL，因为 NULL 在主键里互不相等，同一组合的秒数就加不到同一行上。

### 2. 查询只读这张表，找分类的方法不变

`day_category_time` 和 `top_apps` 只查 `daily_usage`。第 2 步找分类用的还是原来那段 SQL（`from_stats_category_sql`），只是数据来源从 `activities` 换成了 `daily_usage`。原来另外查跨午夜记录的那条 SQL 删掉。

### 3. 分类不存，查询时现找

用户改了网站规则或者应用分类，下次打开页面，这 4,863 行就会按新规则归类，表本身不用动。要是存了分类，每改一次规则都得重算整张表。

### 4. 表怎么保持最新：触发器记下哪几天变了，查询前重算这几天

| 时机 | 做什么 |
|---|---|
| `activities` 插入、删除一行，或者改了日期、设备、进程、网站、秒数、起止时间、忽略标记 | 触发器把这一行涉及的日期（开始那天到结束那天，改之前和改之后的都算）记进 `daily_usage_stale` |
| 查询之前 | 把记下的那几天算进 `daily_usage`，只算这几天，然后清掉标记 |

- **为什么用触发器**：写 `activities` 的地方有采集、同步拉取、忽略规则、删除、启动修复等十几处。触发器由数据库保证每一处写入都会被记下，以后新加的写入也一样。

### 5. 不参与同步

每台电脑都从自己的 `activities` 算出这张表，而 `activities` 里已经有同步来的行。

## 结果（在真实数据库的副本上实测）

| | 改前 | 改后 |
|---|---|---|
| 全部历史，统计 SQL | 391 ms | 8 ms 以内 |
| 月统计，统计 SQL | 55 ms | 1.8 ms 以内 |
| 查询前重算今天 | — | 0.8 ms（记录最多的一天 2.7 ms） |
| 改了忽略规则后第一次查询，重算全部 160 天 | — | 134 ms |

重算的两项是在内存数据库上量的，真实磁盘上会慢一些。

- **迁移 v46**：建 `daily_usage`、`daily_usage_stale` 两张表和触发器，再把所有日期记为变过。升级后第一次查询时整表算出来。
- **磁盘**：表不到 1 MB，每年约增加 1 MB。

## 兼容和以后的约束

- **退回旧版**：旧版不读这两张表，但触发器留在库里，旧版运行时照样记日期。之后再升级，第一次查询会重算这些日期，表仍然是对的。
- **不能用 `INSERT OR REPLACE` 写 `activities`**：它删掉旧行时，默认不会触发删除触发器。旧行和新行的日期不同时，旧行那天就不会被记下，那天会一直算错。
- **以后哪条迁移要重建 `activities` 表，必须把触发器一起重建。**
- **以后改了重算的方法，要在迁移里把所有日期记为变过**，让整表重算一遍。某一天算错以后，如果那天再也没被改动，它不会自己变对。
- **隐私**：没有新增上传的内容。表里的数据本来都在 `activities` 里。
