# LanguageModel: the interface for calling models

> **Status**: Draft. For the overall structure, see [AI backend architecture](0-ai-architecture.md).

Every model is called through this one interface. The model is opened by `LanguageModelProvider` (see [Model selection and configuration](3-settings.md#22-backend-languagemodelprovider)). This document defines the request, the result, the capability description, and the errors. It states what each item means. For how each provider translates them, see [Adapter specification](4-adapters.md).

---

## 1. Types

```rust
/// Functions that every model must implement.
pub trait LanguageModelOps {
    fn capabilities(&self) -> &Capabilities;
    /// Estimates how many tokens a piece of text has. ReportContext uses it to trim to the budget.
    fn estimate_tokens(&self, text: &str) -> u32;
    async fn generate(&self, req: Request) -> Result<Response, ModelError>;
}

/// The model after it is opened. The methods receive this.
pub enum LanguageModel {
    ChatCompletions(ChatCompletionsModel), // Cloud providers and the local llama-server. The local one carries an EngineGuard
    AppleFm(AppleFmModel),
    #[cfg(test)]
    Fake(FakeModel),                       // Replies according to a script
}

pub struct Request {
    pub system: String,
    pub messages: Vec<Message>,
    pub tools: Vec<ToolSpec>,          // Empty = do not provide tools
    pub output: Output,                // Text | Json(schema)
    pub reasoning: Reasoning,
    pub max_output_tokens: u32,        // Upper limit of the answer text. Does not include thinking
    pub temperature: Option<f32>,      // Suggested value for the task
}

pub enum Message {
    User { text: String, images: Vec<ImageRef> },
    Assistant { text: String, call: Option<ToolCall>, carry: Option<Carry> },
    ToolResult { call_id: String, content: String },   // call_id is ToolCall.id
}

pub enum Reasoning { Default, Off, Low, Medium, High, Max }

pub struct Response {
    pub text: String,
    pub call: Option<ToolCall>,        // At most one
    pub carry: Option<Carry>,          // Content the next step must bring back unchanged
    pub effective_reasoning: Reasoning, // The thinking level that actually takes effect
    pub usage: Usage,
}

pub struct Usage {
    pub input_tokens: Option<u64>,     // None if the model does not report it
    pub output_tokens: Option<u64>,    // Includes thinking
    pub reasoning_tokens: Option<u64>,
    pub elapsed_ms: u64,
}

/// Tells the model which tool this is and how to call it. Generated by Tools. The adapter translates it into each provider's format.
pub struct ToolSpec {
    pub name: String,                  // For example, "get_timeline"
    pub description: String,           // Description for the model. Written in the prompt language
    pub parameters: serde_json::Value, // JSON Schema of the parameters
}

/// One call sent by the model. The parameters have not been checked yet.
pub struct ToolCall {
    pub id: String,                    // Cloud: given by the provider. Local: numbered by the adapter
    pub name: String,
    pub arguments: serde_json::Value,
}
```

Put the `text`, `call`, and `carry` from a `Response` into one `Message::Assistant`, unchanged. That is the history for the next step.

## 2. Thinking

### Meaning of the levels

| Level | Meaning |
|---|---|
| `Default` | The adapter sends no thinking field. The model uses its own default |
| `Off` | Explicitly turned off |
| `Low` … `Max` | Explicitly turned on, and the strength increases in order |

### Three rules

1. **Fallback**: When the model does not have the requested level, use the nearest higher level it has. If it has no higher level, use its highest level. For a model that only has a switch, any strength equals "on".
   - Example: DeepSeek does not have `Medium`. Use `High`. OpenAI does not have `Max`. Use `High`.
2. **The adapter may rewrite the level**: When the rest of the request does not allow thinking, the adapter changes it to an allowed level. It reports that level in `Response.effective_reasoning`.
   - Example: OpenAI Chat Completions cannot think when tools are included. The adapter forces `Off`.
3. **Thinking takes up the budget**: See [section 3](#3-output-budget).

### "Auto" is not in this layer

The "Auto" that the user sees in the interface is converted to `Default` or `Off` by automatic configuration before the call (see [Model selection and configuration](3-settings.md#3-logic-automatic-configuration)). The adapter only does a mechanical translation. It does not decide.

## 3. Output budget

Input and output share the same context. The output limit must be set first. Only then is it possible to calculate how much input can fit (#245). The limit also gives a stopping point to a model that does not stop.

`max_output_tokens` is the upper limit of the answer. Thinking also counts as output. When the limit is only enough for the answer, the answer is empty. So when the model may think (including `Default`), the adapter sends the larger of the answer limit and the thinking minimum. When thinking is definitely off, the adapter sends only the answer limit.

- Thinking minimum: 12288 for cloud, 4096 for local (see [Adapter specification 3.2](4-adapters.md#32-other-items)).
- How much input can fit is calculated from the limit that is sent.
- The adapter decides the field name.

---

## 4. Conversation history and bringing content back unchanged

Some models require this: on the next step of the tool loop, the assistant message from the previous step must be brought back unchanged, including the thinking content. If it is missing, the request is rejected.

`Carry` is the place that holds this content.

- The adapter hands it over in `Response.carry`. The upper layer does not read it or change it. The next step puts it back into `Message::Assistant.carry`.
- Only the adapter that produced it can read it.
- If the model is changed in the middle of the conversation, `carry` is dropped. The adapter rebuilds this message from `text` and `call`.

---

## 5. Tool calls

- **At most one call per step.** When the model returns more than one at once, the adapter keeps only the first. `carry` also keeps only the first.
- **The upper layer does not know how tools are implemented.** The capability description only has `tool_use: bool`. Whether to use native tools or grammar is decided per model when the model is opened. See [Adapter specification](4-adapters.md#2-chat-completions-protocol-layer-rules).
- The definition, validation, and execution of tools are not here. See [How AI reads data](3-data-access.md#2-tools).

---

## 6. Structured output

`Output::Json(schema)` requires the model to output JSON that matches the schema. Providers differ in what they can guarantee:

| `structured_output` | What is guaranteed |
|---|---|
| `Strict` | The output always matches the schema |
| `Loose` | The output is always JSON. Fields are not guaranteed |
| `None` | No guarantee. You can only rely on the prompt |

- For every kind, the upper layer must check the result itself after it receives it.
- A request with tools cannot also require `Json`.

## 7. Capability description

```rust
pub struct Capabilities {
    pub on_device: bool,                       // Runs on this machine: local models and Apple FM
    pub context_length: Option<u32>,           // Context length (tokens). None = unknown
    pub tool_use: bool,
    pub structured_output: StructuredOutput,   // Strict | Loose | None
    pub vision: bool,
    pub reasoning: ReasoningSupport,
}

impl ReasoningSupport {
    /// Which levels can be selected for this model. With or without tools, the result may differ.
    pub fn levels(&self, with_tools: bool) -> Vec<Reasoning>;
}
```

- **Decided for each specific model, not for each provider.** Different models from the same provider can have different capabilities.
- **Where each value comes from.** Take the first one that has a value, in this order:
  1. Filled in by the user in the cloud connection
  2. Read at runtime: the context length of Apple FM, and the context length that the local engine reports after it starts
  3. Detected when the connection is tested
  4. The built-in table of known models
  5. Unknown
- **What to do when it is unknown**: automatic configuration gives a conservative default (see [Model selection and configuration](3-settings.md#3-logic-automatic-configuration)).
- The thinking level dropdown in the interface gets its contents from `levels()`.

## 8. Errors

| Error | Meaning | Who handles it |
|---|---|---|
| `Unavailable(reason)` | The system does not support it, the model is not downloaded, the engine is not installed, or the user is not logged in | ① Show the reason |
| `ContextOverflow` | The input exceeds the context length | Not decided yet, see [To be decided](#10-to-be-decided) 1 |
| `Refused` | The content was blocked by the model or the provider | Not decided yet, see [To be decided](#10-to-be-decided) 1 |
| `RateLimited` | Still rate-limited after the retries are used up | ① Show it |
| `Auth` | The key is wrong, or the login has expired | ① Guide the user to the settings |
| `Empty(code)` | The model wrote no answer text, with an `[LLM_EMPTY_*]` error code | The frontend shows a message based on the code |
| `Transport` | A network problem | ① Show it |
| `Provider(original text)` | Other errors returned by the provider: the model does not exist, a server error | ① Show the original text |

- How each provider's errors map to this table is the adapter's job. See [Adapter specification](4-adapters.md).
- Rate limits (429) and disconnects are retried in the model request transport of ⑤. The upper layer only sees the final result.

## 9. Other conventions

- **Cancel**: Discard the future of `generate`. The HTTP implementation does this by closing the connection. The in-process implementation (Apple FM) tells the lower layer to stop on Drop.
- **Streaming**: It is only a way to transport the data. The result is returned once. If chat later needs to show text character by character, add another method. Do not change `Request`.
- **Temperature**: `temperature` is the suggested value for the task. When the provider does not accept it, the adapter does not send this field.
- **Dispatch**: Each kind of model implements `LanguageModelOps`. The `LanguageModel` enum holds them together. The enum also implements `LanguageModelOps`: each function is one `match`, and it forwards to the matching branch.
  - ② receives the enum. It does not use generics.
  - When a trait has an async function, making it `dyn` requires the `async-trait` dependency. An enum does not need it.
  - To add a kind of model, add one branch. A plugin cannot add a model implementation.
  - `LanguageModelProvider` and `ReportContext` are written the same way.
